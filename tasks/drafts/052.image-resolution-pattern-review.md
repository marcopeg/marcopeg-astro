# 052 · Design Review: Image Resolution Pattern

**Status:** draft

## Problem Statement

`src/utils/images.ts` maintains a hand-curated `Record<string, any>` that maps every
public-style path (e.g. `/content/images/2026/02/some-image.jpg`) to a static ES import
of the corresponding file in `src/assets/images/`. The file currently has ~180 individual
import statements and a matching map object.

The motivation was correct: Astro's `<Image />` component requires a statically-imported
`ImageMetadata` object at build time — you cannot pass a bare string URL to it. The map
was the only way to bridge frontmatter string paths to optimised asset imports.

The problem: the map must be manually kept in sync with the filesystem. Any rename,
addition, or deletion of an image file breaks the build silently (the fallback returns
the raw string, so the hero image silently disappears instead of throwing an error).

---

## Findings

### 1. Is a manual static-import map ever the right pattern in Astro?

**No.** It was a reasonable first workaround, but Astro has had `import.meta.glob` since
day one. The correct pattern for "I have a folder of images and I want to map their paths
to `ImageMetadata` at build time" is:

```ts
const images = import.meta.glob<{ default: ImageMetadata }>(
  '/src/assets/images/**/*.{jpg,jpeg,png,gif,webp,svg,avif,png}'
);
```

This produces the same Record automatically, at zero maintenance cost. Vite resolves all
matching files at build time, so the constraint is satisfied without manual imports.

### 2. What is the recommended Astro 5 pattern for hero images?

Two valid approaches, in order of recommendation:

**A) `src/assets/images/` + `import.meta.glob` (optimised)**

- Images live in `src/assets/` and are processed by Sharp.
- The glob builds the map dynamically; no manual upkeep.
- Hero images get responsive `srcset`, WebP conversion, blur placeholders, etc.
- **Caveat:** frontmatter paths must ultimately resolve to a real file. The current
  path convention (`/content/images/YYYY/MM/filename`) does not match the glob key
  (`/src/assets/images/filename`). Mapping is done by filename (see recommendation below),
  which requires filenames to be globally unique — which they already are in this repo.

**B) `public/` only (unoptimised, simplest)**

- Images live in `public/content/images/YYYY/MM/` exactly as frontmatter says.
- `<Image src={heroImage} />` is replaced with `<img src={heroImage} />`.
- No build step needed. Frontmatter paths are served verbatim.
- You lose responsive images, WebP conversion, and OG card optimisation.
- Fine for a personal blog that prioritises simplicity over Lighthouse scores.

### 3. Should `src/utils/images.ts` exist at all?

It should exist, but be rewritten. The current content (180+ manual imports) is
unmaintainable. The `getImageAsset()` function and the single entry point for
path→asset resolution is a good pattern — it's the implementation that needs replacing.

### 4. What is the minimal maintainable solution?

Replace the manual import list with a `import.meta.glob` map. Map lookup by filename
(extracted from both the glob key and the frontmatter path) handles the
`/content/images/YYYY/MM/` → `/src/assets/images/` convention mismatch automatically.

The existing `getImageAsset()` signature stays identical — no changes needed in
`BlogPost.astro` or any call site.

---

## Recommendation

**Replace the manual import map in `src/utils/images.ts` with `import.meta.glob`.**

```ts
// src/utils/images.ts
import type { ImageMetadata } from 'astro';

// Eagerly load all images from src/assets/images/ at build time.
// Vite resolves these statically — no manual imports needed.
const globMap = import.meta.glob<{ default: ImageMetadata }>(
  '/src/assets/images/**/*.{jpg,jpeg,jpeg,png,gif,webp,svg,avif}'
);

// Build a filename → ImageMetadata map.
// This bridges frontmatter paths like /content/images/2026/02/foo.jpg
// to the actual asset at /src/assets/images/foo.jpg.
// Assumption: image filenames are globally unique (true in this repo).
const byFilename: Record<string, () => Promise<{ default: ImageMetadata }>> = {};
for (const [key, loader] of Object.entries(globMap)) {
  const filename = key.split('/').pop()!;
  byFilename[filename] = loader;
}

export async function getImageAsset(
  path: string | undefined
): Promise<ImageMetadata | string | undefined> {
  if (!path) return undefined;
  const filename = path.split('/').pop();
  if (filename && byFilename[filename]) {
    return (await byFilename[filename]()).default;
  }
  // Fallback for public/ assets (blog-placeholder-*.jpg etc.)
  return path;
}
```

**Callers must await the result.** `BlogPost.astro` and any other component that calls
`getImageAsset()` must be updated to `await` it (they are all Astro server components,
so this is trivial).

### Tradeoffs

| | Manual map (current) | `import.meta.glob` (recommended) | `public/` only |
|---|---|---|---|
| Maintenance | High — every image needs a manual entry | Zero — all files auto-discovered | Zero |
| Image optimisation | ✅ (when entries are correct) | ✅ | ❌ |
| Build-time safety | ❌ silent fallback | ✅ missing file = build error | ✅ |
| Filename uniqueness required | No (keys are full paths) | Yes | No |
| Refactoring cost | None | Low — update `images.ts` + await callers | Medium — remove `<Image>`, change layout |

### Files to change

1. `src/utils/images.ts` — replace with glob-based implementation above
2. `src/layouts/BlogPost.astro` — `await getImageAsset(heroImage)` (two call sites: `socialImage` and hero `<Image src=...>`)
3. Any other component or page that calls `getImageAsset()` synchronously

### Out of scope

- `Img.astro` already uses a raw `<img>` tag and a string `src` prop — it does not use
  `getImageAsset()` and requires no changes.
- Inline images in MDX posts use `/content/images/...` paths served directly from
  `public/` — no change needed.
- The filename-uniqueness assumption should be validated before merging (a one-liner
  check in CI, or just a glob count).
