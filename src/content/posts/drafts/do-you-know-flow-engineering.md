<p>I envision a new step in Software Development that I call <strong>Flow Engineering</strong>.<br><em>(but be prepared, this is a challenge to the status quo of Life as we know it)</em></p><p>In <strong>Vibe Coding,</strong> I use natural language to explain to an Agent <strong>how to evolve a codebase</strong>, and then I run the codebase and test it.</p><p>In <strong>Flow Engineering,</strong>&nbsp;I use natural language to instruct an Agent on <strong>how to resolve a request</strong>. I focus on the logical steps and conditions and completely let go of the code entirely.</p><blockquote class="kg-blockquote-alt"><strong>Do not try and change the codebase.<br>That's impossible. <br>Instead, only try to realize the truth... <br>There is no code!<br><sub>The Matrix (give or take)</sub></strong></blockquote><p>The Agent takes a request, pipes it through my explanation – the prompt – and generates the answer on the fly. I could be tool calling, using an MCP, or loading new SKILLs. The Agent can develop code and then run it (and perhaps cache it), or it can use its agentic nature to craft the answer directly.</p><p><strong>The resulting system is explicitly a prototype. </strong></p><p>It doesn't scale, and it is not supposed to. It doesn't focus on performances or security. It focuses on the correct interpretation of intent and execution of flow.</p><p>An ideal Flow Engineering environment should let the Operator describe what should be done, the expected input format and its variations, and the output. And the tests that should be fulfilled to call it "good enough". All of this should be expressed in <em>Natural Language</em>, or maybe we could still use schemas for inputs and outputs and plain prose for the flow part.</p><p>The outcome? <br><strong>Fantastic Documentation!</strong></p><p>Each capability of such a system - think of a REST endpoint - would be a well-written and already tested user story. If the Operator can explain it correctly to an Agent, the same content will be a valuable input to the Engineering Team for building the "real implementation".</p><p>In the context of Flow Engineering, then, <em>the real implementation becomes just an artifact of good documentation</em>, much like a binary file is an artifact of a passing build.</p><blockquote class="kg-blockquote-alt">High-quality code is the byproduct of<br>High-quality intent and documentation.</blockquote><p>In the context of Flow Engineering, the Operator becomes much closer to a Product Manager, with enough technical understanding to <strong>translate Intent into Flow documents</strong>, without the need for formal languages or a complex environment. </p><p>Today, I often witness a gap between Product Management and Software Engineering. It's a communication gap, and <strong>too many meeting hours are spent in clarifying Intent</strong> and verifying the expected Flow. IMHO, that's wasted time.</p><p><strong>When a PM/PO builds a prototype</strong> by explaining to an AI what should be done and letting the AI question back the WHYs, the interaction will naturally remove ambiguity, reducing the time we all spend in tedious meetings.</p><p>Engineers will be able to <strong>focus on the complex problems</strong> of securing, scaling, and making a solution economically viable. Most of the user stories have already been vetted and clarified by the Agentic system. The expected outcome is visible as working requests with realistic answers. Not to mention that contracts, tests, and maybe even code prototypes might be provided as well!</p><p>In short, Vibe Coding is for nerds. Flow Engineering is the missing link between Product Managers and Engineering Teams.</p><p>And once the Engineering Team accepts an epic/story for implementation, it's <em>Spec-Driven Development all the way to production</em>. </p><p>But that's another story.</p>
